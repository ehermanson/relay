# AGENTS.md — Relay

## Rules

- **Self-maintenance**: After any codebase change, check whether AGENTS.md and/or README.md need updating. Stale docs are worse than no docs.
- **Plan mode**: Make the plan extremely concise. Sacrifice grammar for the sake of concision. At the end of each plan, give a list of unresolved questions to answer, if any.
- **Workflow**: For anything beyond a trivial fix, create or pick up a task before starting work. Tasks live in `.relay/tasks/<id>.md` in the current Space’s worktree. Prefer `relay tasks` for validated offline writes; set `in_progress` when starting and `done` when finished. Never edit a different worktree’s task to track this Space’s work.

## Ubiquitous Language

Use `UBIQUITOUS_LANGUAGE.md` as the canonical glossary for domain terminology in user-facing language, docs, UI copy, issue discussion, and agent responses.

High-risk distinctions:

- **Project** = top-level codebase
- **Space** = branch-scoped collaboration area within a project
- **Chat** = user-facing conversation
- **Managed session** / **External session** = runtime behind a chat
- **Complete** = merge and close a space
- **Archive** = close a space without merging

## Project Overview

Relay is a bridge between remote devices and local AI coding agents. It manages multiple agent processes, discovers external sessions, and serves a React web UI.

**Three-layer structure:**

- `app/` — React UI (the product)
- `server/` — HTTP, WebSocket, auth, tunnel + `server/core/` (engine: managers, types, providers)
- `cli/` — CLI wiring (bin.ts, migration.ts)

## Architecture Philosophy

In the backend, Relay manages providers through a provider-driver registry (`server/core/provider-registry.ts`): each provider declares its capabilities and owns session creation, model lookup, transcript parsing, external-session discovery, and managed-session recovery behind the shared `ProviderSession`/`ProviderRuntimeBinding` contract. The UI asks the server for available providers (`GET /api/providers`) and provider-scoped model metadata plus capabilities (`GET /api/provider-models`), then shows or hides toolbar controls and picker options from that metadata.

**Key architectural invariants:**

- Relay is multi-provider. Never assume a behavior is Claude-only or Codex-only without checking the provider contract and the sibling driver(s). For provider-facing changes, either update every affected provider path or document why the behavior is genuinely provider-specific.
- `ProviderCapabilities` is the single source of truth for what controls the UI should render — never hardcode provider-specific logic in the UI
- SQLite has two distinct roles: `sessions` is a rebuildable Claude transcript index, while `managed_sessions` is the source of truth for managed-session provider bindings and restore metadata
- JSONL files on disk are the canonical transcript source — the DB is a cache/index that can be rebuilt by scanning `~/.claude/projects/`
- Core (`server/core/`) must never import from server; server imports from core; UI imports from core via `@shared` alias
- Session targeting after first response always uses `--resume <sessionId>`, never `--continue` (which picks the most-recently-modified session in CWD — wrong with concurrent sessions)

## Tech Stack

- **Runtime**: Node.js 22+, ESM only (`"type": "module"`), native TS execution in dev
- **Language**: TypeScript (strict mode)
- **Server**: `node:http` host server + Hono for HTTP routing + `ws` for WebSockets
- **UI**: React 19 + Vite + Tailwind CSS v4 + React Router
- **Tests**: Node.js built-in test runner (`node --test`)

## Build & Test

```bash
pnpm build          # tsc + vite build
pnpm build:server   # tsc only
pnpm build:app      # UI typecheck + vite build
pnpm typecheck      # server + UI TypeScript checks
pnpm test           # node --test test/*.test.js
pnpm dev            # server from TS source (no tsc) + vite dev
```

Always `pnpm build:server` before `pnpm test` — tests import from `dist/`.

Tests must never write to the real `~/.relay`. Every test file imports `test/test-env.js`, which redirects `RELAY_WORKTREE_BASE` to a temp dir and hardens the git env, so running a single file with `node --test` is also isolated. As a backstop, `getWorktreeBase()` falls back to a temp dir whenever `NODE_TEST_CONTEXT` is set. New test files should start with `import "./test-env.js";`.

`pnpm ci-check` runs the full CI gate locally in order (`build → typecheck → lint → task checks → test`; build first so tests see fresh `dist/`). A Husky `pre-push` hook (`.husky/pre-push`) runs it automatically **against the pushed commit, never the working tree**: `scripts/check-commit.sh <sha>` checks the commit out into a temporary worktree (sharing `node_modules`, so a lockfile change still needs a real install first) and runs `pnpm ci-check` there — a partial commit of a dirty tree can depend on untracked files and pass in place while failing in CI, and this way the main checkout's `dist/` and dev server are untouched. The hook **skips** when the pushed commits touch only docs/non-code files (`*.md`, `*.txt`, `docs/`, etc.) — task Markdown still runs the lightweight `pnpm tasks:check` gate, and any other changed path forces the full check. Bypass with `git push --no-verify` only when you know CI will pass.

### Dev Mode

`pnpm dev` runs the server directly from TypeScript source via Node's native type stripping (`--conditions=relay-dev` remaps `#` imports to `.ts` files). No `tsc --watch`, no `dist/` dependency, no auto-restart. Press `r` to manually restart the server.

This avoids the "using the tool to work on the tool" problem — AI agents modifying server files won't trigger disruptive mid-operation restarts.

Dev state is isolated: `pnpm dev` defaults `RELAY_HOME` to `~/.relay-develop` (override by setting `RELAY_HOME`), so a dev server never shares `sessions.db`, `provider-state.json`, or worktrees with a production install using `~/.relay`. Two servers writing the same home causes last-writer-wins state clobbering and schema-version DB rebuild ping-pong.

### External Session Discovery

- InstanceManager polls provider-specific external discovery every 30s; drivers currently use `ps` + `lsof` and exclude managed PIDs plus any descendant of the Relay server process (SDK-managed CLIs don't expose a PID, so `ppid` ancestry is the only reliable exclusion — without it, external instances get mispaired with managed subprocess PIDs and takeover SIGKILLs a managed session)
- **Codex adds a second, PID-less signal** (`server/core/providers/codex-discovery.ts`): any rollout under `~/.codex/sessions` in a registered cwd whose mtime is within `DISCOVERY_INTERVAL × STALE_THRESHOLD` counts as a live external session with `pid: undefined`. Codex Desktop hosts threads inside ChatGPT.app, so there is no `codex` process with the project cwd to find — without this, those sessions surface only at the startup scan. This is deliberately not applied to Claude: Claude Code always runs as a `claude` process with the project cwd, so PID discovery is complete there. `readCodexSessionMeta` reads only the first line (rollouts are tens of MB; `session_meta` alone is ~20KB) and caches by path. Two exclusions keep the signal honest: **sub-agent rollouts** (`thread_source: "subagent"` / `source.subagent`, from `multi_agent` spawns) are never sessions of their own — skipped by discovery and the startup scan — and PID-less discovery skips rollouts whose `originator` is Relay's own (`RELAY_CODEX_ORIGINATOR`, the app-server `clientInfo.name`), since Relay's threads are managed by definition.
- **Codex rollout format is versioned by the CLI.** ≤ 0.152 records conversation turns as `event_msg` `user_message` / `agent_message` / `agent_reasoning`; ≥ 0.153 records `event_msg` `item_completed` with typed v2 items (`UserMessage`, `AgentMessage`, `Reasoning`, …) and no longer writes the legacy events. `extractCodexConversationMessage` (`codex-transcript.ts`) normalizes both and is the single reader for replay, scan-time titling, and last-message previews — never match on `user_message` directly. Do **not** read turns from `response_item` `message` entries: those include Codex's own user-role injections (`<recommended_plugins>`, `<environment_context>`). The **single exception** is a sub-agent rollout (`session_meta` says subagent via `isSubagentSessionMeta`): its assignment exists nowhere else in plaintext, so replay records — never emits as a turn — the first user-role `response_item` that doesn't start with a `CODEX_INJECTED_USER_PREFIXES` entry (`codex-transcript.ts`; `<recommended_plugins>`, `# AGENTS.md`, `<environment_context>`, `<user_instructions>`, `<space-context>`, `<permissions instructions>`, `<collaboration_mode>`, `<turn_aborted>`, `<skill`). Keep that list conservative: when in doubt, add the prefix and omit rather than show injected context. Normal (root) rollouts never take this path. The scan-time meta reader streams the file head (up to 1MB) because 0.153 front-loads ~90KB of prompt/context before the first real user turn.
- `scanAllSessions()` walks provider transcript roots (`~/.claude/projects/`, `~/.codex/sessions/`) on startup for historical sessions
- `decodeProjectDir()` uses greedy filesystem-validated decode (not naive `-` → `/`) to handle dashed project names
- JSONL watchers track incremental changes with dedup: suppressed while process is active, offset advanced to EOF when process finishes

### Chat Titles

- **Claude Code names its own sessions; Relay adopts that name.** The CLI appends `{"type":"ai-title","aiTitle":…}` to every SDK-launched transcript a few seconds after the first prompt (a background Haiku-class summary, re-appended when re-evaluated) and `{"type":"custom-title",…}` on `/rename`. `server/core/providers/claude-session-title.ts` reads them (head + tail windows; last record wins, custom beats AI). They have no `timestamp` and never enter history. Three readers: the startup scan (`name` + `summary` on the `sessions` row), turn end (`doRefreshTitle`), and the transcript watcher — which applies title records even mid-turn, when it otherwise leaves the stream to the process. The old `sessions-index.json` lookup is gone; the CLI no longer writes that file.
- **A recorded title is authoritative and the fallback never replaces it** — a short one like "Fix CI" would otherwise read as "trivial" and the two would churn. Without one, the title is the **first** substantive user message (`firstSubstantiveUserText`: human-authored, not injected, not "ok"/"commit this"), and it only ever _upgrades_ a default or trivial name. Never retitle from the latest message: that produced chats called "ci failed" and "ok. commit and push".
- Relay's own `customTitle` (rename in the UI) blocks every automatic source. Codex has no server-side naming — `thread/name/updated` only arrives when some client (Codex TUI/Desktop) set a name via `thread/name/set`; generating Codex titles with the user's own Codex account is a tracked follow-up, never a Claude/Haiku dependency (a Codex-only user has no Claude install).

### iOS Standalone Top-Edge Blur

`index.css` defines `--app-top-inset`: the native safe-area inset plus 22px in iOS standalone mode (`@supports (-webkit-touch-callout: none)` plus `display-mode: standalone`). The body and viewport-fixed overlays (sidebar, sidecar, drawers, dialogs, image viewer) consume this one value. New viewport-edge content must use it instead of reading `env(safe-area-inset-top)` directly; nested headers must not apply it again. Dialog and image height limits account for the same inset. This leaves the system's blurred top band empty rather than trying to disable it. Safari Web Inspector on the affected iPhone (Safari 27) showed no filter/backdrop-filter/transform on the header or its ancestors; moving the unchanged header down 22px made it crisp, while 16px still blurred the top of the title. Browser tabs and desktop do not get the extra 22px. The feature gate also applies to older iOS versions and iPadOS; it deliberately avoids version sniffing.

Previous sticky/safe-area ownership changes did not fix the reported blur. WebKit bug 301756 describes Safari toolbar color extension, not a guaranteed standalone-PWA blur opt-out. A temporary fixed-header test was reported unchanged, but was gone on inspector reconnection, so that result is inconclusive. Keep this as a measured clearance workaround; do not claim the native effect is disabled. Preserve the existing body safe-area ownership and keyboard behavior.

### iOS Keyboard Handling

The iOS keyboard is handled by **accepting** WebKit's native page push (the header slides off-screen while typing — standard iOS webapp behavior) and making scroll math visual-viewport-aware instead of mutating layout. The message-framing effect in `message-list.tsx` intersects the scroll container with `window.visualViewport` to compute the pin position (`messageTop − hiddenTop`), spacer size, and handoff threshold. Dead ends — tried and reverted (see git history), don't relearn them:

- iOS standalone PWAs do **not** resize the layout viewport for the keyboard (and ignore `interactive-widget=resizes-content`); they shrink the visual viewport and push the page via `visualViewport.offsetTop` + window scroll
- Reactive countermeasures jitter: `scrollTo(0,0)` fights an animated push (and `html { scroll-behavior: smooth }` animates the correction); transform-following the offset moves the focused input and re-triggers WebKit's reveal (feedback loop)
- Pre-shrinking `<body>` on `focusin` prevents the push, but iOS freezes web-content compositing during the keyboard presentation, so the shrink paints only after the transition settles (~1s perceived stall) — web-unfixable
- Pre-shrinking at `pointerdown` paints in time but moves the tap target mid-gesture — iOS abandons the tap (no focus, no keyboard)

**The composer never steals focus on touch devices.** Passive focuses — opening a chat (draft restore), a plan or question arriving — are gated by `shouldAutoFocusComposer()` (`app/src/lib/composer-focus.ts`, false on `pointer: coarse`), because a programmatic focus raises the keyboard and pushes the page. Focuses that follow a tap (suggestion cards, editing a queued message, "reply with text") stay unconditional. There is a second, less obvious focus path: Lexical writes its editor-state selection into the DOM on commit, and placing a range inside an unfocused contenteditable focuses it. `SyncEffect` in `composer-editor.tsx` therefore tags selection syncs with `skip-dom-selection` whenever the editor is blurred (`editor.focus()` re-applies the state selection later, so desktop behavior is unchanged). Symptom before the fix: opening an already-hydrated chat raised the keyboard (the composer mounted synchronously inside the tap, within iOS's user-activation window) while one that had to load didn't.

### Native Mobile Composer Experiment

Settings → General has a per-browser, localStorage-backed toggle (`useNativeMobileComposer`, `app/src/hooks/use-native-mobile-composer.ts`) that swaps the Lexical `ComposerEditor` for `ComposerTextarea` (`app/src/components/chat/composer-textarea.tsx`) on `pointer: coarse` devices. Why: iOS autocorrect fires `insertReplacementText`, which Lexical `preventDefault`s and re-applies itself (controlled mode), so WebKit loses its correction bookkeeping — no tap-to-undo, weaker predictive text — and every keystroke also runs a sync `localStorage` write plus a full input-area re-render. The textarea shares `ComposerEditorProps`/`ComposerEditorHandle` and honours the same controlled-value contract: a programmatic `value` change is echoed through `onChange` exactly once (the `_pendingProgrammaticValue` guard in `useComposerState` waits for that echo, otherwise the next keystroke would be dropped as a stale echo), and a pending `selectionOffset` is applied only while focused (stashed until `onFocus` otherwise — setting a selection on an unfocused textarea can raise the keyboard). Mentions and slash commands are plain text there; the menus still work because they operate on `draftText` + caret, not on chips. It is an A/B experiment, not a product decision — remove one path once the comparison is done.

### Mobile Type & Touch Targets

Mobile (≤768px) sizing is centralized in `app/src/index.css` — don't fight it per-component:

- A 17px root font plus a **mobile type ladder** that remaps the small rem utility classes (`text-[0.5625rem]`…`text-[0.8125rem]`, `text-xs`) up one step on phones. Use the rem scale for new text — never px sizes like `text-[11px]` (they silently opt out of the ladder). Deliberate px exceptions: the composer and chat message bodies are pinned to 16px (iOS anti-zoom parity), xterm and the diff drawer set their own mobile sizes.
- A `@media (pointer: coarse)` block gives menu items / options / tabs native hit heights centrally; undersized icon buttons get `max-[768px]:h-10 max-[768px]:w-10`-style bumps at the call site. Keep interactive targets ≥ ~40px on mobile — grow hit areas (padding/min-height), not glyphs.
- **Tooltips never open on touch.** Anything informational needs a tap path on mobile (e.g. context-panel help icons switch to a `Popover` on coarse pointers), and hover-gated affordances need a `pointer: coarse` override (see `sidebar.css`).
- Dialogs top-anchor on mobile (`dialog.tsx`) — the keyboard covers vertically centered dialogs.
- Mobile overlays (sidebar, sidecar) use the shared `SwipeableDrawer` (`app/src/components/ui/swipeable-drawer.tsx`): motion-drag swipe-to-dismiss with a progress-driven backdrop, plus opt-in edge-swipe-to-open. Don't hand-roll new overlay gestures — reuse it. Its edge listeners never block taps (they claim the gesture only after horizontal intent), but the OS back-gesture can win at the outermost bezel, so a tap affordance must always exist too.
- `SwipeableDrawer` owns scroll containment: a capture-phase `touchmove` guard cancels any touch that isn't inside an _overflowing_ `overflow-y: auto/scroll` element, and `[data-swipeable-drawer] * { overscroll-behavior: contain }` stops edge bounce chaining into the page. Two rules keep it working on iOS: (1) the guard never cancels inside a real scroller, not even at its edges — iOS decides on the first `touchmove` and a cancelled first event kills the whole gesture, so a 1px jitter at `scrollTop` 0 would dead-end every scroll; (2) the panel is a stretched flex column — never give it a percentage height (WebKit won't reliably resolve one through a row-flex item, and a collapsed panel means content never overflows, so touches scroll the page instead). Drawer content must be a genuine scroller filling the panel via `flex-1 min-h-0`.

### Composer Attachments

- Video formats and the 100 MB video limit live in `server/core/video-attachments.ts`, shared by the composer, upload client, and file routes. Photos/documents retain their 10 MB limit.
- Videos have composer previews and inline chat playback, but travel as `attachments` / `[File: source: ...]` through the shared provider path, never as `images` or native video model input. Both Claude and Codex receive the local file path. Browser codec support determines playback; the chat keeps a file link as fallback.
- `/api/file` streams video responses with single byte-range support for seeking. Draft video blobs use the existing IndexedDB attachment store; revoke their object URLs just like image previews.

### Offline Drafts, Outbox & Push

- Composer text drafts live in `localStorage` (with `sessionStorage` fallback for seeded/legacy drafts); attachment drafts remain in IndexedDB. A disconnected send stores text and Blob attachments in the separate `relay-outbox` IndexedDB store before clearing the composer. Keep the app open for reconnect delivery; the service worker handles push only, not offline app-shell boot or background sync.
- `OutboxProvider` drains across chats after reconnect/reload. It uploads Blob attachments, then posts to `/api/outbox/:id`. `outbox_receipts` in `SessionDB` is authoritative for send IDs: reserve before dispatch, mark accepted afterward. A reservation without acceptance is **uncertain**, never automatically retried. Outbox sends require an idle chat because the existing mid-turn queue is memory-only. Connected sends retain WebSocket queue/edit/interrupt semantics. Preserve outbox owner identity and per-row lease when changing this flow.
- `PushNotifications` owns VAPID keys and subscriptions in a private `push-notifications.json` next to the DB. Subscriptions belong to auth sessions and are removed when revoked or expired. The service worker shows user-visible notifications with same-origin chat links. Browser permission is requested only from the Settings click; iOS/iPadOS requires a Home Screen installation. Visible clients publish short-lived presence so their device gets in-app state instead of push. No silent push suppression in the service worker.

### Tool Result Previews

- `ActivityMessage.toolUseId` carries the provider call identity on both tool uses and results (Claude SDK/CLI and transcript replay; Codex app-server items and rollout calls). Preserve it through new provider paths: parallel tools can finish out of order, so matching by the most recent tool attaches results to the wrong file.
- Claude SDK tool results normally arrive in `user.message.content`, including array-of-text-block content; process them even when `tool_result_meta` is absent. Assistant-envelope results remain supported.
- The chat reducer matches results by ID across activity groups; legacy events without IDs use unmatched calls in emission order. Read previews show captured result text with file-language highlighting. Read/ViewImage image previews retain their thumbnail even when the result includes text; errors show the result instead.

### Delegated Agent Cards & Agents Sidecar

Collapsed cards and Agents sidecar rows resolve missing models through `useAgentModelLabel` → `GET /api/instances/:id/agents/:agentId/model`. Provider drivers read a bounded transcript head (1MB, cached by mtime/size) for Claude assistant-model records or Codex turn-context metadata; full child history remains expansion-only. The shared query retries missing active-agent metadata every 15s and refreshes on completion/re-completion. Expanded history also seeds that model cache, so metadata discovered there reaches collapsed surfaces. Live `AgentInfo.model` takes precedence; no parent/default model is guessed.

Delegated work (subagents, teammates, peers) is rendered from one shared state fed by the provider-agnostic contract in `types.ts` (`AgentInfo`, `AgentUpdateMessage`, `MessageAuthor`, `agentId` attribution on output/activity/user messages). Pure helpers live in `app/src/lib/agents.ts` (tested in `agents.test.ts`); the `/sandbox` route has a "Delegated agents" section with realistic scenes (`agent-sandbox-fixtures.ts`) — prototype card changes there first.

- **Visual identity is one system across every surface.** `agent-avatar.tsx` owns the shared look: `getAgentAccent(agent)` picks a deterministic accent from the categorical `--color-chart-*` palette (keyed by name, falling back to the agent key; chart-5/red is skipped so identity never reads as failure), and `AgentAvatar` renders a tinted monogram chip that pulses (`animate-ring-pulse`) while the agent is active. Card, sidecar row, and `AgentNote` all use it, so the same agent is the same colour everywhere and concurrent agents are told apart at a glance — colour is decoration only, never a status signal.
- **Status stays quiet unless it wants attention.** `AgentStatusBadge` (`agent-status-badge.tsx`) renders a dot + label with no filled chip; only running / needs-input / failed carry a saturated colour, so a wall of finished agents reads calm. `getAgentStatusPresentation` maps lifecycle → label/colour and is the one place status wording lives.
- **Two surfaces, two intents.** The collapsed in-chat `AgentCard` is two compact lines (identity + model over a quiet second line) for lightly following along; the Agents sidecar (`AgentsPanel`) leads with a status roll-up bar (running / needs-input / failed / done counts) over the same rows for triage. The second line is the "what's it doing / what was it for" glance: live activity while working, the failure reason on failure, and the agent's **purpose (its description) once finished — never a truncated dump of the report**, which reads as useless boilerplate ("SONNET AGENT REPORTING: …") when clipped. The full report is one expand away.
- **The report and the assignment each live in exactly one place.** `AgentDetail` is the dig-in view: a compact meta strip (no model — the header already shows it, so it's repeated only when unknown), a line-clamped collapsible Assignment, an Activity trace, and the Result. A child's transcript normally opens with the assignment (as its own first user turn) and closes with the final report (as its last assistant turn); `trimActivityEchoes` strips both from the Activity trace (loose whitespace-insensitive match) so the assignment shows only in Assignment and the report only in Result — never twice. Activity collapses by default for a finished agent (dig-in) and is open while it works.

- **State shape** (`useInstanceMessages`): `agents: Record<agentId, AgentInfo>` (sparse upsert via `mergeAgentInfo` from `@shared/agent-info` — the **one** merge shared with the server; omitted fields keep their previous value, `usage` merges field-wise, nothing is defaulted) and `agentItems: Record<agentId, ChatItem[]>` (nested transcripts). Both maps are replaced, never mutated, so consumers (the `Sidecar` memo comparator, `MessageList` memos) compare them by reference — there is no version counter.
- **Routing rule**: any `output`/`activity`/`user` message with `agentId` is appended to `agentItems[agentId]` with the same accumulation logic as the main stream (`createReplayStream` for replay, `append*` helpers live) and **never** enters `items`. Attributed messages also never touch the main turn's processing flags — a child's `isWaiting` does not end the orchestrator's turn. Child `task_list`/`file_list` activities are dropped (the sidecar panels describe the main chat). Any `exit` entry — clean or not — flushes the in-flight assistant text/activity group during replay; otherwise a restarted session's first response is glued onto the interrupted one.
- **Anchoring rule**: an agent whose `originToolUseId` matches a `tool_use` in the stream renders as an `AgentCard` _in place of_ that entry (`ActivityGroup` reads the `toolUseId → agentId` index from `AgentCardsContext`, provided by `MessageList`; the merged `tool_result` becomes the card's `fallbackResult`). On first sighting of an `agent_update` with no origin, or an origin not yet in the stream, the reducer inserts **one** `agent-card` item keyed by `agentId`; `buildAgentAnchorIndex` excludes carded agents, so a late-arriving origin can't produce a second card (edge: the plain tool_use then stays visible alongside the inserted card). **Nested delegation never gets a main-stream card**: an agent with `parentAgentId`, or whose origin `tool_use` lives inside another agent's transcript (`isMainStreamAgent`), renders only inside its parent's detail — otherwise a grandchild would appear twice.
- **Cards are never folded**: `ActivityGroup`'s "N more" collapse counts only plain entries; anchored agent cards always render, so a failure or "Needs approval" badge can't disappear behind the fold. Card props come from `AgentCardsContext` (`agentItems`, `instanceId`, `provider`, `pendingAgentId`) — `AgentCard`/`AgentDetail` take only `agent`, `fallbackResult`, `depth`, so every surface that renders them must sit inside a provider.
- **Authorship**: `UserMessage.author.kind === "agent"` produces an `agent-note` item rendered by `AgentNote` ("Message from <name>", left-aligned, `Bot` icon) — never a `user` bubble. `internal` messages stay hidden. The legacy `transcript`/`agent-transcript` path is gone; the server replays those hand-offs as `agent_update`s.
- **Detail on demand**: expanding a card or a sidecar row mounts `AgentDetail`, whose `useAgentHistory` (`GET /api/instances/:id/agents/:agentId/history`, 404/`null` → "No detailed transcript") fetches only then — never on mount, and always (there is no `historyAvailable` flag). Fetched child history is attributed to the child and usually leads with the child's own `agent_update`, so `agentHistoryToItems` selects `agentItems[agentId]` **first** and falls back to the bare main stream only when nothing was attributed; its `agent_update`s are folded into a local agents map so grandchildren render in the detail. The detail's own metadata (model, role, assignment, result, usage) renders from that merged record (`mergeAgentInfo(allAgents[id], agent)`, live fields winning), not the bare `agent` prop — so fields the main history never had but the child transcript supplies (e.g. a Codex child's model/role/assignment) appear once fetched. The query key is `[..., agentId, terminal ? \`final:${revision}\` : "live"]`: the `live`/`final`discriminator forces one fresh fetch when an agent finishes (its running-time snapshot — often partial, sometimes a 404 — is never frozen by the`staleTime: Infinity`that then caches the completed transcript; active agents keep a 15s window + focus refetch), and the`revision`(the agent's`endedAt`) distinguishes successive completions of a **resumed** agent (completed → running → completed) so the second completion isn't served the first's indefinitely-cached transcript. Source preference protects completeness: fetched assistant prose wins unless the live prose contains the entire fetched prefix and extends it (ignoring whitespace and message boundaries). A late live report must not hide earlier fetched work. While active, equal prose with more live items can also show new tool activity; terminal ties prefer the fetched transcript. When only one source has prose it wins; with neither, the longer stream wins. The two are never concatenated. Existing nested `agentId`attribution is preserved when reading a child transcript, and a known grandchild stream is never used as the fallback for an empty child stream.`lastActivity`falls back to the latest attributed`tool_use`through`getAgentLastActivity` when absent or a legacy transport-only label ("Message exchanged" / "Received a message"). Codex interaction receipts never overwrite useful activity. Both collapsed surfaces fall back to description, assignment, then role when no activity is available.
- **Capability gate — one gate at the source**: when `ProviderCapabilities.supportsAgentActivity` is false the UI renders **no** delegated-agent surface at all — no cards, no Agents sidecar tab/toggle. Mechanism: `instance-view.tsx` resolves `agents`/`agentItems` to shared EMPTY maps before they reach the context, so cards, anchored substitution, badges, the header toggle (`hasAgentsContent` = agents non-empty) and the sidecar all read gated state and never check the flag themselves; `MessageList` drops inserted `agent-card` rows whose agent is absent. Model shows only when known ("model unknown" otherwise); labels come from `getAgentModelLabel` → `findProviderModelLabel`. `buildAgentAnchorIndex` early-returns a shared empty map when no agent has an origin (no item scan in the common case); `buildAgentTree` is cycle-safe (agents unreachable from a root are still emitted, so the panel count matches); chat timeline markers cover `agent-card` (labelled by agent title) and `agent-note` rows.
- **Adding a sidecar tab** (the four registration points, all touched for `agents`): (1) `SidecarTab` union + `VALID_TABS` + `FALLBACK_ORDER` in `stores/sidecar-store.ts` and a `has*Content` option in `useSidecarPanels`; (2) `TAB_LABELS` + `renderTabContent` in `sidecar.tsx` (and the sibling `TAB_LABELS` in `spaces/space-sidebar.tsx`); (3) the header toggle in `instance-header.tsx` (`SidecarToggles`), plumbed via `instance-view-header.tsx`; (4) the flag/count on the `InstanceViewContext` `shared` value from `instance-view.tsx`. ### Lazy Hydration

Sidebar/dashboard rows render from persisted SQLite metadata first. Opening a chat triggers lazy hydration of transcript/task/file state and git info, but history reads stay passive: Relay does not boot/resume a stopped managed session until the user explicitly sends a message (or otherwise takes over/resumes it).

With the space action the trigger always opens a menu, so chat creation costs one extra click even when unambiguous.
- The inbox's rules — space grouping, review-chat exclusion, closed spaces counting as done, independent pinned ordering, project filtering — live as pure functions in `app/src/lib/inbox.ts` (tested in `inbox.test.ts`); the hook is a thin `useMemo` wrapper so the logic is testable without mounting the sidebar.
- `ProjectAvatar` falls back to the project's **initial**, not a folder glyph, when there's no scanned favicon — a column of identical folders defeats the point of keying rows by project.
- **The open destination is never hidden**: `capInboxEntries` matches chat IDs or space IDs (including empty spaces); capped lists (15 active / 20 done, "Show all" to expand) append it when it falls past the cap; the Done section auto-expands when you open a chat that was _already_ done; and the collapsed rail — which lists only active chats — appends the open chat when it's done or past its cap.
- **Marking a chat done never expands the Done section** — a collapsed list jumping open under the cursor is worse than the chat scrolling out of view. The acknowledgement is a pulse on the "Done N" header (`.inbox-done-label` in `sidebar.css`), triggered by ids that were in the active list on the previous render — not by `done.length`, which also jumps when the lists first load. The auto-expand above is suppressed by the same signal: having seen the open chat in the active list means a later move into Done was a transition, not an arrival. Both rules live in `app/src/hooks/use-done-section.ts` (tested in `use-done-section.test.ts`), and `useDoneSectionDisclosure` keeps its per-chat reset, its "saw it active" write, and its expand in **one** effect deliberately — split across effects with narrower deps, switching from one active chat to another reset the flag without re-setting it, so the next mark-done expanded the section (intermittently, depending on which chat you came from).
- The row's model label resolves `providerStatus.effectiveModel` → `stats.model` → `preferredModel` and stops there. Do **not** fall back to a project/global default (it would claim a model the chat never ran), and do **not** call `useProviderModelsMap` for labels — discovery can spawn provider processes, so labels come from the pure `findProviderModelLabel` catalog helper.

**Done chats.** `doneAt` is a **timestamp, not a boolean**: `isChatDone()` (`app/src/lib/utils.ts`) treats a chat as done only while its recency is at or below the marker, so later activity revives it with no server-side clearing. Recency (`getChatRecencyTimestamp`) is the **max** of `lastMessage.timestamp` and `lastActivityAt` — either can lead (tool-only activity bumps `lastActivityAt` without a message), and a fallback chain would strand revived chats in Done. The Done section itself orders by recency alone (pins express "keep in front of me", which done chats no longer need). This is deliberate — there is no single choke point where `lastActivityAt` is bumped, so a push-based revive would leak. Chats in `completed`/`archived` spaces are permanently done regardless of activity. Storage mirrors `pinned` exactly: `done_at` on both session tables, mutated only by `SessionDB.setDone()` (excluded from the upserts' conflict-update), exposed via `POST /api/instances/:id/done`, which works for chats with no live instance. **Marking done also releases the chat's process slot** (`stopIdleProcessForDone` → `stopInstance`, the same path as manual pause) — otherwise done chats keep counting against the concurrent-process cap and the user has to pause them by hand. It never interrupts a `processing` chat, and clearing the marker never boots anything (the next message revives it lazily).

**Sweeping stale chats.** A backlog is cleared by hand, never by a rule: the inbox renders a "Mark N inactive chats done" row under the active list when `selectStaleInboxEntries` (`app/src/lib/inbox.ts`, cutoff `STALE_CHAT_DONE_DAYS` = 10) finds anything, and a confirm dialog runs it. Two invariants make it safe to repeat:

- **The client picks the chats, the server just writes them.** `POST /api/instances/done-bulk` takes explicit `instanceIds` rather than a cutoff, because the DB row's `last_activity_at` is only half of a chat's recency — the other half is its last transcript message — so a server-side `WHERE last_activity_at < cutoff` would sweep chats the UI still shows as recent. The sweep is scoped to the filtered `active` list, so it marks exactly what the user is looking at, and skips `processing` chats plus any with recency 0 (unknown, not ancient — that's what a just-created chat looks like).
- **Every swept chat gets the sweep's `now`, not its own last activity.** A chat reads as done only while recency ≤ `doneAt`, so stamping anything older would leave part of the sweep still undone.

`InstanceManager.setInstancesDone()` persists via `SessionDB.setDoneBulk()` (one transaction), updates live instances in memory (they override REST summaries in the UI's merge), and emits a single `instances:changed` → one `instance_list` broadcast. Never emit per-chat status for a bulk mutation — a sweep touches hundreds of rows.

### Search

- ⌘K search (`app/src/components/search-dialog.tsx` → `GET /api/search` → `SessionDB.search()`) is **global by default** — never scope it to the route's project implicitly. The dialog offers a per-open project filter dropdown (reset on every open, never persisted); when unfiltered, results from the current route's project get a 2× rank boost (`boostProjectId`) so local results lead without hiding cross-project hits.
- FTS5 `search_index` ranking: weighted bm25 (title ≫ summary/branch > prompts/messages > transcript, weights on `SEARCH_INDEX_COLUMNS`) × 30-day recency decay. Recency is `max(last_message_at, last_activity_at)` (`RECENCY_SQL`), matching the inbox's `getChatRecencyTimestamp` — keep them in sync.
- The **last token is prefix-matched** (`"tok"*`) unless the raw query ends in whitespace (word complete) — as-you-type search must not require whole words.
- Tokens are ANDed; when the strict query matches nothing (and there are 2+ tokens), `search()` retries with **OR and flags results `partial: true`** — the UI renders them under a "Partial matches" heading instead of a dead "No results".
- An **empty query returns recent chats** (`SessionDB.recentChats()`, same `SearchResult` shape with null snippet), so the dialog doubles as a chat switcher. Ordering is **pinned-first, then recency** (matching `compareChatListOrder`); the index carries a `pinned` column and `setPinned()` resyncs the doc, so pin toggles reflect immediately.
- **Projects and active spaces are search results too**, matched client-side in the dialog (name/branch substring) from the cached `projects` + `["spaces", projectId]` queries — no server round-trip; they render as "Projects"/"Spaces" groups above chats and respect the project filter. Space queries are `enabled` only while the dialog is open.
- Per-chat index updates delete FTS docs **by rowid** via the `search_index_docs` map — never `DELETE … WHERE instance_id = ?` on `search_index` (UNINDEXED columns force a full scan; across every chat on restore/shutdown that cost tens of seconds). Startup reindexing skips transcripts whose `search_content.source_key` (`SEARCH_CONTENT_VERSION` + path + mtime + size) is unchanged; bump `SEARCH_CONTENT_VERSION` when `extractSearchableText` output changes.
- Adding a column to `SEARCH_INDEX_COLUMNS` is self-migrating: `ensureSearchIndex()` drops any existing table missing a declared column and the index is rebuilt at startup.
- Results whose chat has no registered project are hidden client-side — they can't be navigated to (routes need a `projectId`).

### Spaces

Spaces group multiple concurrent agent chats within a shared git worktree/branch (`Project → Space[] → Chat[]`). Every project has an implicit "main" space (no worktree, default branch). Additional spaces create dedicated worktrees in `<RELAY_HOME>/worktrees/space-<id>/` (defaults to `~/.relay/worktrees/space-<id>/`).

- `SpaceManager` (`server/core/space-manager.ts`) owns space lifecycle: create, list, complete (merge + cleanup), delete (archive + cleanup)
- Startup recovery includes archived spaces and honors existing IDs before branch/path matching, so surviving chat metadata cannot reopen closed spaces. Missing worktrees warn only for broken active spaces; completed/archived spaces normally have no worktree and their chats still restore read-only.
- Each space has a "brief" at `.relay/space-context.md` (git-excluded, seeded on creation). Its **contents** are injected into every chat's bootstrap context (the space-level analog of project custom instructions) via `buildSpaceBootstrapContextBlock` + `extractSpaceContextForInjection` — only when the file has authored content beyond the seed template, and only at session start (new/resumed chats).
- `spaces` table in SQLite with `space_id` FK on `sessions` and `managed_sessions`
- **Target branch**: `spaces.base_branch` records the local branch a space merges into (creation base with `origin/` stripped, `HEAD` → current branch; older rows lazily backfilled from the project/global default space branch, then the repo default). `SpaceManager.resolveTargetBranch()` is the one source for Complete, the space diff, and the PR base — never re-derive it from what the main checkout has checked out.
- **Complete** (`mergeBranchIntoTarget` in `git.ts`): stops (never deletes) the space's chats via the injected `setSpaceChatStopper` → `InstanceManager.stopSpaceChats`, auto-commits the space worktree, computes the merge in memory (`git merge-tree --write-tree`), then either fast-forwards the main checkout (only when it has the target checked out) or moves only the branch ref (`update-ref` with CAS). A target checked out in another linked worktree is refused. Only tracked changes/conflicts in the main checkout block; untracked files never block and are never deleted (no `git clean`, no `reset --hard`; legacy in-checkout merges undo with `git reset --merge`). Refusals throw `SpaceCompletionError` (`conflict` carries the file list; route returns 409 `{ errorKind, conflicts, targetBranch }`) and change nothing. The local branch is kept after worktree removal.
- **Worktree removal** (`removeWorktree`) returns `{ removed, method, error }` and never swallows failures; if `git worktree remove --force` fails it deletes the dir only when it is inside the worktree base AND git no longer tracks it (unlisted or dangling `.git` pointer). `sweepOrphanedWorktrees()` runs in the background after the startup scan over `<worktreeBase>/space-*` only: removes dirs whose `.git` gitdir target doesn't exist (skipping unmounted volumes and dirs an active space references); valid-but-unreferenced worktrees are only logged.
- `MergeMethod` type: `"squash" | "merge-commit"` — passed per-merge via `completeSpace(id, { mergeMethod, squashMessage? })`; default is `"squash"`
- `spaces` table stores merge metadata (`merge_commit`, `merge_method`, `merged_at`, `target_branch`), remote tracking (`remote_status`, `pr_url`), `base_branch`, and `pr_status_json` (last known PR snapshot). New columns are added by idempotent `ALTER TABLE` in `ensureSpacePinColumn` — no schema-version bump, no rebuild.
- Lifecycle states: `active` → `completed` (merged) or `archived` (closed without merge); completed/archived spaces are read-only in the UI
- UI terminology: "Complete" (action label), "Merged"/"Archived" (status badges), "Archive" (replaces "Delete" in UI)
- Sidebar shows Active spaces → Chats → Closed spaces (collapsed); mini-sidebar shows active only
- REST API: `GET/POST /api/projects/:dir/spaces`, `GET /api/projects/:dir/spaces/all`, `GET/DELETE /api/spaces/:id`, `POST /api/spaces/:id/complete`, `GET /api/spaces/:id/diff` (404 only for a missing space; git failures return their real status), `GET /api/spaces/:id/pr[?refresh=1]`
- WS messages: `create_space`, `complete_space`, `delete_space` (client); `space_created`, `space_completed`, `space_removed`, `space_list` (server)
- `space_list` broadcast includes all spaces (active + closed) so the sidebar can render the closed section
- Non-default spaces render as clickable items in the sidebar; selecting one opens a tab-based view with horizontal tabs per chat
- Non-git projects fall back to flat Chat[] model (spaces require git)
- `pushSpace()` pushes the space branch and optionally opens a PR (`server/core/space-pr.ts`): `gh --version` + `gh auth status` (runner `auth` kind → not authenticated), then `gh pr list --head <branch> --state open` — an existing open PR is reused (`prAction: "opened_existing"`), never duplicated; otherwise `gh pr create --base <target> --body-file <temp>` (deleted in `finally`).
- **PR status**: `PrStatusReader` reads `gh pr view <url|branch> --json …` (60s cache, 20s→15min exponential backoff on failure, ≤4 concurrent), normalizing checks to passing/failing/pending/skipped counts deduped by workflow+name (newest wins). Refreshed when a space header is viewed and after push; changed snapshots persist to `pr_status_json` (+ `remote_status` `pr-open|pr-merged|pr-closed`) and broadcast via `space_list`. A merged PR is surfaced, never auto-completed. List rows (`SpacePrStateChip`) render only the persisted snapshot — they never call gh.

### Git Integration

- `GitStatusBar` component renders below the project header: branch selector, push/pull/fetch buttons, ahead/behind indicators, dirty-state badge
- **Never `execFileSync` git (or `gh`) on a request, WebSocket, or manager path.** Every call goes through the async runner in `server/core/git-runner.ts` (`runGit` / `runGh`: arg arrays, no shell). It forces a prompt-free env (`GIT_TERMINAL_PROMPT=0`, empty `GIT_ASKPASS`/`SSH_ASKPASS`, `GCM_INTERACTIVE=never`, `SSH_ASKPASS_REQUIRE=never`; `gh` adds `GH_PROMPT_DISABLED=1`) and runs children in their own process group without a TTY, so a timeout kills git plus any ssh/helper it spawned. `readOnly: true` sets `GIT_OPTIONAL_LOCKS=0` so status reads never take `index.lock` from under an agent. Failures throw a typed `GitCommandError` (`kind`: `timeout`/`auth`/`not_a_repo`/`locked`/`output_too_large`/`not_found`/`aborted`/`failed`) with a short redacted message. `server/git-http.ts` maps kinds to HTTP (400/409/502/504/413).
- Timeout tiers live in `GIT_TIMEOUTS` (fast reads 5s, local work 30s, network 120s, worktree/merge 300s). Short calls share a global concurrency cap (8). Longer calls bypass it, so push/merge can't starve status reads.
- Mutations (commit, checkout, fetch/pull/push, merge/complete, worktree add/remove) run inside `withRepoLock(dir, fn)`. The lock is keyed by the git common dir, so all worktrees of one repo serialize, and it is re-entrant: `completeSpace` holds it around its nested helpers. Mutations retry transient `index.lock` errors twice. Reads never lock.
- `server/core/git.ts`: sync helpers are **filesystem-only**, with no subprocess: `isGitRepo`, `getRepoRoot`, `resolveGitDirs`, worktree origin resolution, and `readGitHeadInfo` (HEAD branch for sync restore/scan paths). Everything else is async. `getStatusSummary(dir)` returns branch/upstream/ahead/behind/change counts from one `git status --porcelain=2 --branch -z`; prefer it over separate calls. UI-facing reads report failure instead of faking values: `getCurrentBranch` returns null only for a detached HEAD and throws otherwise, `getAheadBehind` returns null when there is no upstream, and `isWorktreeDirty`/`listBranches`/`listWorktrees` throw. The status endpoints add `hasUpstream`, and the UI shows an error state rather than "up to date".
- Git action buttons (status bar, header badge, space header) are single-flight: a ref blocks double clicks and every action stays disabled until the pending one settles.
- `getPrimaryRemote(dir)` detects the actual remote name (prefers `origin`, falls back to first listed, null when there are no remotes). Never hardcode `"origin"`; `getDefaultBranch`/`getRemoteUrl`/`gitPush` all use it
- Remote branch names are stripped of the dynamic remote prefix (not hardcoded `origin/`)
- REST API: `GET /api/projects/:id/branches`, `POST /api/projects/:id/checkout`, `POST /api/projects/:id/git/fetch`, `POST /api/projects/:id/git/pull`, `POST /api/projects/:id/git/push`
- Space push: `POST /api/spaces/:id/push` with optional `{ createPR: true }`

### Repo Status

- **No UI polling of git endpoints.** Git state is pushed by `RepoStatusService` (`server/core/repo-status-service.ts`): one entry per worktree dir (realpath), ref-counted subscribers, snapshot-first on subscribe, all work (and timers) stopped when the last subscriber leaves. A refresh is one `getStatusSummary` plus one `git diff HEAD --numstat`; the fingerprint hashes status fields, the numstat output, and changed paths' mtime/size (so same-size and untracked edits count). Events publish only when the fingerprint (or `lastFetchError`) changes. Concurrent refresh requests coalesce (in-flight + dirty flag).
- Triggers only — no file watcher, no short interval: first subscribe; `invalidateRepoStatus(dir)` (agent turn end, diff-stat enrichment, SpaceManager via `setRepoStatusInvalidator`); every mutation run under `withRepoLock` (`onRepoMutation` in `git-runner.ts`, so commit/push/pull/fetch/checkout/merge/worktree ops are covered centrally); a finished background fetch. Invalidation refreshes every subscribed worktree of the same repo (git common dir).
- **Background fetch** while a repo has subscribers: `git fetch --quiet --no-tags <primaryRemote>` under the repo lock with a 15s timeout, at most once per 60s per repo, failures back off 30s → 15min, skipped (never queued) while a mutation holds the lock or a fetch is in flight. Failures never surface as errors — only `lastFetchError`/`lastFetchedAt` on the snapshot. Disabled under the test runner and by `RELAY_BACKGROUND_FETCH=0`.
- WS: client `repo_status_subscribe` / `repo_status_unsubscribe` with `target` = `{kind:"instance",instanceId}` | `{kind:"space",spaceId}` | `{kind:"project",projectId}` (server resolves the dir; `server/repo-status-targets.ts`); server `repo_status { target, status: RepoStatusSnapshot | null, error? }`. Subscriptions die with the socket. REST fallback: `GET /api/repo-status?instanceId=|spaceId=|projectId=`.
- UI: `useRepoStatus(target, { invalidate: [queryKeys] })` (`app/src/hooks/use-repo-status.ts`) ref-counts one wire subscription per target, re-subscribes per connection, and invalidates the given react-query keys when the fingerprint changes (first snapshot is the baseline). The header badge/diff drawer (`instance-git-status`, `instanceDiff`), `GitStatusBar` (`branches`) and the space diff (`spaceDiff`, also refreshed when the drawer opens) use it; focus refetch remains a fallback. A failed space diff is an error state with retry, never "no changes".
- **Per-edit diff stats are debounced.** `file_list` is emitted immediately with last-known per-file stats; `InstanceManager.fileStatsDebouncer` (`KeyedTrailingDebouncer`, 800ms quiet / 5s max wait, never overlapping per chat) runs one `enrichDiffStats` pass outside the chat's mutation queue and emits a replayable `file_stats` message, which the UI merges into `currentFiles` without touching processing state. Turn end and hydrate force an immediate pass. The watcher's 2s branch check reads HEAD from the filesystem (`readGitHeadInfo`), never spawning git.

### Provider Version Advisories

### Delegated Agent Work

Subagents/teammates are represented through one shared contract in `types.ts`: `AgentInfo` (sparse upsert via `agent_update`, replayable), `agentId` attribution on `OutputMessage`/`ActivityMessage`/`UserMessage`, and `UserMessage.author`. `ProviderCapabilities.supportsAgentActivity` is the **single gate**: when false, the UI renders no cards, notes, or Agents sidecar (see the UI section above); both providers currently set it. The provider-neutral merge/fold helpers (`mergeAgentInfo`, `collectAgentsFromHistory`, `findAgentKeyByProviderId`) live in fs-free `server/core/agent-info.ts`, shared with the UI via `@shared/agent-info`, so live reducer, replay, and REST can never disagree about a merge.

- **The Relay agent key is provider-chosen and opaque.** Claude: the spawning `Agent`/`Task` tool_use id (known before the provider's own id, and equal to `parent_tool_use_id` on live child frames). Codex: the child thread id. `providerAgentId` carries the native id (Claude `agentId`/`task_id`) for history lookups and permission matching; `ProviderRequest.relayAgentId` is the mapped key. There is no `historyAvailable` flag — the child-history route's 404 is the availability signal.
- **Attributed messages never enter the main stream, and never drive chat state.** Anything with `agentId` belongs to that agent's nested transcript. Claude live (`claude-sdk.ts`) keys every stream accumulator by `parent_tool_use_id ?? "root"` (`AgentStreamState`) and sets `forwardSubagentText: true`; a child's `message_start`/`message_stop` never resets root bookkeeping (`_lastMessageHadToolUse`, thinking counters, usage), and `send()` resets only the root accumulator — a background child may be mid-message across user turns. `hasStreamedText` is set only by the stream flush, never by the assistant-frame fallback, so child text that arrives frame-only emits every message. Child `TodoWrite`/`TaskCreate` frames become plain activities — they must not rewrite the chat's task list. In `InstanceManager`, live `output`/`activity` with `agentId` (and the watcher equivalents) are pushed to history and broadcast only: no `processing` flip, idle-stop, plan-file capture, `pendingPermission`, title refresh, or preview — otherwise a background child keeps the chat "processing" forever after the root turn went idle (`test/instance-agent-events.test.js`).
- **Authorship is explicit; transport role never decides it.** `server/core/agent-messages.ts` is **Claude-specific** (used by the SDK driver and by `parseJsonl`'s `convertUserEntry`, which only runs on Claude transcripts; Codex has `codex-agent-activity.ts`). `classifyUserEnvelope` is the single classifier for both live and replay: `origin.kind` peer/observer/coordinator → `UserMessage { author: { kind: "agent", name } }` with the `<agent-message>` envelope and instruction wrapper stripped (prefer `origin.body`); `task-notification` (origin or `<task-notification>` XML) → `agent_update { status, result }`, never a user bubble; `auto-continuation`/`observer-activity` → hidden. Classify **before** `stripInternalTags` — the envelopes are themselves "internal" XML. Absent `author` = human. The SDK driver skips user frames during resume replay (`_isResumeReplay`, like assistant frames) — replayed peer notes/notifications are already in history.
- **Builders are shared** (`buildAgentSpawnInfo`, `buildAgentResultInfo`, `buildTaskNotificationInfo`) so live (`tool_use_result`, system `task_notification`, user-envelope XML) and replay (`toolUseResult`, transcript XML) emit identical updates: `async_launched` → `running` + `providerAgentId` + `resolvedModel`; sync completion → `completed|failed` + report text + `usage`. `input.model` is copied verbatim (aliases stay aliases; `resolvedModel` overrides later). **Not every background task is an agent** — `local_bash` tasks emit the same `task_*` events — so a task event maps to an agent only when its `tool_use_id` is an already-known agent key, its `task_id` resolves via `findAgentKeyByProviderId`, or the event is agent-shaped (`subagent_type`, or `task_type` naming an agent/workflow); the bare `task_id` is never a key. Replay mirrors this: a `<task-notification>` maps to an agent only when its `<tool-use-id>` names an agent already folded into the parse context, or its `<task-id>` resolves via `findAgentKeyByProviderId` (the async-launch result recorded the task id as `providerAgentId`) — a notification matching neither (e.g. a `local_bash` background task's) is dropped, never keyed by the bare tool-use or task id. Agent lifecycle survives a compaction boundary: the pre-boundary lightweight pass still registers delegation spawns and their results (folding agents into the shared parse context) while eliding ordinary tool detail, so a synchronous agent that ran entirely pre-boundary keeps its card and result. `agent_update.raw` is a small provenance stub (`{ tool?, toolUseId?, subtype? }`), never the provider payload — that would duplicate the tool result across the WS, replay ring, and client raw store. Unknown stays unknown — no status guessed from silence, no model from defaults.
- **Child history is on-demand and file-based**: `GET /api/instances/:id/agents/:agentId/history` → `InstanceManager.readAgentHistory` → driver hook `readAgentHistory` (`provider-registry.ts`). Claude parses `<projectDir>/<sessionId>/subagents/agent-<providerAgentId>.jsonl` through the **cached** transcript parser (mtime/size LRU) and stamps `agentId` only on unattributed messages, preserving grandchild attribution; Codex reads the child rollout (`readCodexAgentHistory`). Reading never boots/resumes a session and never mutates `Instance.agents`; grandchildren announced in a child transcript go into a lookup-only `Instance.nestedAgents` so their own history stays resolvable. `readAgentOutputResult` (background `.output` files) tail-reads in growing windows and memoizes by (path, mtime, size). `GET /api/instances/:id/agents` always folds the (cached, passive) history and overlays the live map — live is the patch over the transcript, since the JSONL lags the SDK stream.
- Provider drivers emit `agentUpdate` and `userMessage` (agent-authored or child-attributed only) on `ProviderSessionEvents`; InstanceManager pushes both into history and broadcasts (`instance:agent_update` → WS `agent_update`, replayable). The legacy `TranscriptMessage`/`instance:transcript` path is gone: the "Full transcript available at:" hand-off replays as an `agent_update` with `result` (key `transcript:<file stem>`). Dashboard previews, titles, and the provider-switch handoff skip child-attributed messages; the handoff flattens `agent_update.result` and agent notes.

### Codex Multi-Agent (Collaboration) Items

- **Thread scoping is mandatory.** One app-server connection carries the root thread (`_sessionId`) plus every spawned child thread. `handleNotification` gates on `params.threadId`: root → normal handling; a _known_ child (announced by `subAgentActivity` / `collabAgentToolCall` / `thread_spawn` metadata) → attributed handling of `turn/*`, `item/*`, `item/agentMessage/delta` only; anything else scoped to a non-root thread is dropped with a debug log — never merged into the root stream, never allowed to touch `_currentTurnId`/`finishTurn`/stats. `thread/started` never overwrites an already-set root id.
- Child text streams into per-`<threadId>:<itemId>` buffers and flushes as `OutputMessage { agentId }` on the child's `agentMessage` completion (or its `turn/completed`); it never passes through the `ProposedPlanStreamParser`. Child tool items are stamped `agentId` via `emitActivity`; `file_list` stays unattributed (workspace-level).
- `server/core/providers/codex-agent-activity.ts` is the single normalizer for both spellings (`SubAgentActivity`/`CollabAgentToolCall` snake_case in rollouts, `subAgentActivity`/`collabAgentToolCall` camelCase live) and for collaboration `function_call`s (`spawn_agent`, `send_message`, `wait_agent`, …; `wait` → `wait_agent`). Live and replay emit the same sequence: a root `tool_use` (`toolUseId` = call id, the card anchor), `agent_update`s, then a `tool_result`. Ids coincide across shapes (spawn's `call_id` == `SubAgentActivity(started).id`), so both paths dedupe the tool_use **and** the tool_result by id (`collabIds` / `collabResultIds` in replay — a `function_call_output` and a typed `CollabAgentToolCall` can both appear, in either order; the output wins when its call is pending because it carries the result text). `SubAgentActivity.kind` → lifecycle: `started` running, `interacted` lastActivity, `interrupted` stopped, `completed` completed. Codex `agentId` is the child **thread id**; `name` is the `agent_path` leaf (the orchestrator's `task_name`), not `agent_nickname`.
- **Lifecycle comes from the provider, not the tool verb.** `CollabAgentToolCall.agents_states` values are Codex `AgentStatus` variants (0.154 binary, serde snake*case): bare strings `pending_init` / `running` / `interrupted` / `shutdown` / `not_found`, or single-key objects for the data-carrying `{"completed": "<final text>"}` / `{"errored": "<reason>"}` — **not** `{status}` records (a legacy record shape is still accepted). `parseCodexAgentStatus` + `mapCodexAgentStatus` (`codex-agent-activity.ts`) map them: running→running, pending_init→pending, completed→completed (+`result` from the payload), errored→failed (+`statusDetail`), shutdown/interrupted/cancelled→stopped, `not_found`/unknown→no status. The verb only fills in when the provider said nothing: `spawn_agent`→running (failed spawn→failed, since the agent never started) and `close_agent`→stopped. A failed `resume`/`send`/`wait` is the \_call* failing (`lastActivity: "… failed"`), never the agent. `wait_agent` results are how children leave `running`. Live, a child `turn/completed` parks it as `waiting` unless a terminal state was already reported; `emitAgentUpdate` folds patches with the shared `mergeAgentInfo` (`#core/agent-info.js`).
- **`thread/started` re-keys the root only while `thread/start`/`thread/resume` is in flight** (`_rootThreadRpcPending`): a resume can come back under a new id, and rejecting it would drop every root notification as "unknown thread". Once the connection is established, a divergent `thread/started` is a child candidate (trusted only with `thread_spawn` metadata).
- **`agent_update.raw` is a provenance stub** (`codexAgentUpdateProvenance`: `type`/`id`/`tool`/`kind`/`status`), never the provider item — it would duplicate `result`/`assignment` text. Activities keep their sanitized `raw`.
- **Encrypted content is never shown.** In 0.154 rollouts `spawn_agent.message`, `send_message.message`, and MESSAGE/NEW_TASK bodies are Fernet tokens (`gAAAAA…`). `isCodexEncryptedText` gates every string that could be one; `input` is sanitized to plaintext fields (`task_name`, `target`, `timeout_ms`), replay entries for these carry no `raw`, and live `raw` goes through `sanitizeCodexCollabRaw`. An encrypted MESSAGE bumps `lastActivity` only. Child → parent reports are `response_item agent_message { author:"/root/<name>", recipient:"/root" }` with a `Message Type: …\nPayload:\n` header (`parseCodexAgentReport`): FINAL_ANSWER payload is plaintext → `agent_update { status:"completed", result }`; plaintext MESSAGE → `UserMessage { author:{kind:"agent"} }`. Authors resolve to thread ids via `agent_path` seen earlier in the same file.
- **Child history is file-based and read-only**: `readCodexAgentHistory(codexDir, threadId, { rootThreadId? })` (`codex-transcript.ts`) locates `rollout-*-<threadId>.jsonl`, parses it, prepends an `agent_update` from `session_meta` (`source.subagent.thread_spawn`; `model` comes from `turn_context` — the child meta has none) plus the assignment (first user-role `response_item message` that isn't a Codex injection — `<recommended_plugins>`, `# AGENTS.md`, `<environment_context>`, …), stamps `agentId` on everything, drops the child's `SubAgentActivity`/`agent_message` traffic _about its parent_, and nests grandchildren via `parentAgentId`. Never `thread/read`, `thread/resume`, or boot anything to serve it. `isSubagentSessionMeta` still excludes child rollouts from standalone discovery. Two caches keep it cheap: thread id → rollout path (validated with `existsSync` on every hit, dropped on a miss, so the `~/.codex/sessions` walk runs once per child) and path → parsed history keyed by mtime+size (a child still being written is re-parsed only when its file changes; `clearCodexAgentHistoryCache()` for tests).
- **The incremental JSONL watcher carries the collaboration parse state across entries.** `convertCodexTranscriptEntry`'s dedup sets (`collabIds`, `collabResultIds`) and the `agentPaths` map (`/root/<name>` → child thread id) live on `WatchState` (`codexCollabIds`/`codexCollabResultIds`/`codexAgentPaths`), not in a per-entry context — a spawn and its result, or a child's `agent_message` report and the `SubAgentActivity` that registered its author path, arrive on **separate** JSONL lines. Without persistence a FINAL_ANSWER can't resolve its author and collab tool_uses/results double-emit. Because watching starts at EOF, those maps are **seeded once** from the pre-EOF transcript on the first watched entry (`seedCodexWatcherMappings`, guarded by `codexMappingsSeeded`): it re-parses only lines containing `gent`/`ollab`/`spawn` into a throwaway context sharing the `WatchState` maps and discards the output — so an agent spawned before Relay attached still has its author path available when its later report arrives.
- Unverified on the live wire (0.154): whether child-thread notifications arrive on the parent connection at all, and how a child's report is delivered live (handled defensively as an `agentMessage` item carrying `author`). Replay is verified against real rollouts.

### Claude Config Dir (Accounts)

- **One resolution, used everywhere.** `resolveClaudeConfigDir()` (`server/core/providers/claude-cli.ts`) is the only source for the Claude config dir: `CLAUDE_DIR` > `CLAUDE_CONFIG_DIR` > `~/.claude`. It feeds `providerDirs.claude` (transcript scan, watchers, plans, external-session pairing, user skills, `.claude.json`) **and** every CLI spawn through `buildClaudeSpawnEnv(configDir)`, which pins `CLAUDE_CONFIG_DIR` in the child env (SDK sessions, prewarm/model probes, the legacy process, `claude mcp add`). Never spawn `claude` with raw `process.env` and never `join(homedir(), ".claude")` directly.
- Why: Claude Code keeps one login per config dir, so a machine with a personal and an enterprise account switches with `CLAUDE_CONFIG_DIR`. Resolving the dir independently on the read and spawn sides made Relay pair terminal chats from one account while starting new chats under the other.
- **The default dir has two logins.** Claude Code keys its stored credentials (and global config) by whether `CLAUDE_CONFIG_DIR` is _set_: an explicit `CLAUDE_CONFIG_DIR=~/.claude` is a different keying from the unset default, even though it is the same directory. Multi-account users typically alias `claude` to set the variable for every account, so their "default" login lives under the explicit keying and the unset one is empty — and vice versa for everyone else. Relay never guesses: `claudeConfigDirEnvMode` (`claude-cli.ts`) is `explicit` for every non-default dir, and for the default dir it is whatever the login probe found signed in (`recordClaudeConfigDirEnvMode`), falling back to the server's own env. `prewarmSdk` and `probeClaudeAccountIdentity` run `inspectClaudeLogin` under the preferred keying first and the other one if that is logged out (`candidateEnvModes`); `buildClaudeSpawnEnv(configDir, env, mode)` then sets or removes the variable accordingly. Symptom before: a work login that `/status` showed fine read as logged out inside Relay, and new chats ran under whatever the _other_ keying held.
- "Signed in" is any auth signal from `accountInfo()` (email/org/plan, or an auth path — enterprise gateway, API key, third-party backend, reported in `account.status`, never `label`) **or** a `get_usage` snapshot, which only answers for an authenticated subscription. `tokenSource`/`apiKeySource` are the literal `"none"` when unused — never a sign-in signal. When nothing answers, the log prints the raw `accountInfo` so a new shape can be mapped.
- `findClaudeBinary` prefers the PATH-resolved `claude` (what the user's shell runs) over the well-known install paths, and validates every candidate is an executable file — `which` in an interactive zsh prints alias definitions, and one leaked into `RELAY_CLAUDE_CLI_PATH` once.
- **Account profiles** (`ProviderCapabilities.supportsAccountProfiles`, Claude only today): a profile is a labelled config dir (`ProviderAccountProfile`); the server's resolved dir is the implicit `default` profile and is never stored. User-added profiles live in `global_settings.provider_profiles_json`, mutated only by `/api/providers/:provider/profiles` (GET/POST/PATCH/DELETE, `POST …/:id/probe`) — never by `PATCH /api/settings`. Identity (email · org · plan) is **probed, never typed**: `probeClaudeAccountIdentity(configDir)` in `claude-sdk.ts` runs `startup()` + `accountInfo()` under that dir's env, cached per dir (30 min, in-flight deduped) and separate from the default-dir caches. Pure helpers (`listAccountProfiles`, `resolveAccountProfile`, `findProfileForConfigDir`, `accountProfileRoots`) live in fs-free `server/core/account-profiles.ts`, shared with the UI via `@shared/account-profiles`.
- **A chat is bound to one dir for life.** `createInstance` resolves explicit `profileId` > `Project.defaultProfileId` > `providerDefaults[provider].profileId` > default and sets `InstanceInfo.configDir` only for a non-default profile (persisted in `managed_sessions.config_dir`); a resume follows the root that already holds its transcript. Every per-instance driver context goes through `providerDirsFor(instance)` (session creation, `--resume`, transcript capture/path, agent history/model reads, plan lookups) so the CLI and the reader always agree. Deleting a profile clears project/global references but never touches `managed_sessions`.
- **Discovery walks every profile root.** `getClaudeRoots()` (default first) drives `scanAllSessions`, external-session pairing (`claudeRoots` on the discovery context — candidates from every root, newest wins), `resolveProjectId`/artifacts/plans; `refreshAccountProfileRoots()` rescans when a root is added. External chats get `configDir` derived from their `jsonl_path` at summary time (not stored), so terminal chats are labelled by account too. Model discovery/prewarm stay on the default dir.
- UI: Settings → Providers → **Accounts** (`account-profiles.tsx`: identity line always visible, "Use for new chats" radio → `providerDefaults.profileId`, add/rename/remove/re-check, polls while a probe is unsettled), Project Settings → **Account** select (`defaultProfileId`), and a quiet account chip in the chat header / context panel — rendered only with the capability **and** ≥2 profiles, so a single-account install never grows a chip. Codex has the same concept (`CODEX_HOME`) but does not advertise the capability yet.

### Model Discovery

- For **every** provider, the provider-discovered model list is canonical: new models surface in discovery order without a code change. `BUILTIN_PROVIDER_MODELS` (`provider-catalog.ts`) is offline fallback + metadata enrichment only — a new model release must **not** require a catalog bump.
- Claude canonical ids come from the SDK's `resolvedModel` field (with the `[1m]` alias suffix stripped); display-text scraping in `inferClaudeModelIdFromSdkInfo` is a legacy fallback for old CLIs. Label formatting (`formatClaudeModelLabel`) accepts any `claude-<family>-<version>` id — never whitelist family names.
- Both discovery caches re-probe in the background on a 30-min TTL, kicked from the drivers' `getModels` (`refreshSdkDiscoveredModelsIfStale` in `claude-sdk.ts`, `refreshCodexModelsIfStale` in `codex-models.ts`), so a long-running server picks up new models without a restart. This matters because lists change out from under a running server: Anthropic publishes models server-side; Codex lists change when the CLI is updated (including via Relay's own provider-update flow).
- Claude SDK spawns (sessions and discovery probes) prefer the **system-installed** `claude` CLI via `pathToClaudeCodeExecutable` (`resolveClaudeExecutablePath` in `claude-sdk.ts`). The CLI bundled inside the `@anthropic-ai/claude-agent-sdk` package caps flagship alias resolution at whatever it shipped with and only changes on a lockfile bump; the system CLI auto-updates and is covered by the provider-version advisory. Escape hatch: `RELAY_CLAUDE_SDK_USE_BUNDLED_CLI=1` forces the bundled CLI.

### Model Options

`ProviderModelOptions` (`reasoningEffort`, `fastMode`) is the canonical contract for provider-agnostic model tuning. Provider drivers map these to provider-specific session args.

- `InstanceInfo.modelOptions` is canonical
- `model_options_json` column on `managed_sessions` is the canonical storage for provider-agnostic model tuning
- `set_model_options` WS message does sparse merge (omitted = untouched, `null` = clear)
- `ProviderCapabilities` includes control metadata (`reasoningEffortLevels`, `runtimeModes`, `fastModes`) — UI renders labels/descriptions from these, never hardcodes provider-specific text
- Claude `auto` is an environment-dependent runtime mode: expose it only for Bedrock, Vertex, Foundry, or explicit `CLAUDE_CODE_ENABLE_AUTO_MODE` opt-in, and never when user settings contain `disableAutoMode: "disable"`.
- `ReasoningEffort` uses `"max"` as the Relay-canonical highest effort; provider drivers map to native values (e.g. Codex `"xhigh"`); unknown strings pass through
- Mid-session model switches emit a `model_switched` system event (divider in chat + timeline). It's recorded at **message-dispatch time** (`recordModelSwitchOnDispatch`), not when the user picks a model in the UI — only when the resolved model differs from the previous turn's (`instance.lastTurnModel`). So toggling the picker without sending, or switching away and back before sending, produces no divider; the divider always sits directly above the first turn the new model ran. Relay-level events like this never appear in provider transcripts, so they're persisted in the `session_events` table and re-merged into history by `mergeSessionEvents()` on every hydrate/getHistory. `lastTurnModel` is in-memory only, so the first send after a server restart re-establishes the baseline without a divider

### MCP Discovery

- `ProviderMcpServerStatus` is Relay's normalized MCP discovery contract. Keep configured, available-to-chat, and connection/authentication state separate; presence in Provider configuration never proves Chat availability.
- Provider-global MCP state may enrich Chat-reported state, but Chat-reported state is authoritative for availability in that Chat. Empty arrays clear stale snapshots; `undefined` means the Provider supplied no new knowledge.
- Provider-native MCP payload parsing stays in Provider drivers/session initialization. Shared UI consumes normalized enums and `ProviderCapabilities.mcp`, never Provider-name branches or raw status-string parsing.
- Global Settings can add Provider-global MCP servers through `POST /api/providers/:provider/mcp-servers`; Claude supports HTTP/SSE/stdio and Codex supports HTTP/stdio. `server/core/mcp-management.ts` validates inputs and invokes Provider CLIs shelllessly; never accept credentials embedded in URLs or client-supplied commands. Relay intentionally does not remove MCP configuration because Provider discovery does not reliably distinguish user-managed, plugin-owned, and bundled servers.
- Project Settings shows every installed MCP-capable Provider because Provider-global servers still apply to Project Chats. Project-scoped add controls render only when the Provider advertises Project management scope.
- Claude Project discovery merges shared `.mcp.json` configuration with local-scope configuration stored under the Project path in `~/.claude.json`. Reads must return sanitized summaries only: never expose header, argument, or environment values, URL credentials, or query-string secrets.
- Relay does not launch interactive MCP authentication/logout from the server: headless Provider CLI login can block indefinitely. When a server needs authentication, the UI directs the user to the Provider CLI. Live-only reconnect and enable/disable controls do not belong in Global Settings.
- MCP add routes validate the requested transport against `ProviderCapabilities.mcp.management.transports`. Global and Project Settings share the same capability-driven MCP form so their supported fields cannot drift.
- Codex may reference a bearer-token environment variable by name. Relay does not accept or persist token, header, or environment values. Persistent request-timeout and tool-policy settings remain unavailable until the Provider management surfaces expose a safe portable contract.

### Task Tracking

- Canonical tasks are tracked Markdown files with YAML front matter: `.relay/tasks/<id>.md`; terminal history lives in `.relay/tasks/archive/<id>.md`. Discussion is separate, append-only files in `.relay/task-discussion/<task-id>/<comment-id>.md`.
- Tasks have Project-wide identity and branch-specific state. Each Space reads/writes its own worktree. Project Tasks defaults to the Main space; API callers select another Space with `?spaceId=`. Never use the Main space path for a chat running elsewhere.
- For this repository, create/pick up a task for nontrivial work (see Workflow above). Relay's generic bootstrap default does not require every request in every Project to create a task; explicit Project instructions override that default.
- Prefer the offline `relay tasks` CLI: `list --ready --json` for work discovery, `show <id>` for detail, `update <id> --status in_progress` / `done` for progress, `comment <id>` for reports. No server or network is required. Read only selected tasks and their relevant dependencies, not the entire archive.
- Schema v2 keeps `id`, `title`, Markdown description/body, `priority` (0–4, P0 first), `type` (epic|task|bug), `tags`, `parent`, `blockedBy`, `createdAt`, `updatedAt`, and nullable `closedAt`. Stored status is open|in_progress|done|cancelled; blocked is derived. Existing eight-hex and safe legacy slug IDs remain stable; new tasks use UUIDs. Revisions are content hashes, never manually incremented counters.
- Cancelled blockers remain unresolved. Cancelling a task does not satisfy its dependents. Delete only tasks with no incoming references; otherwise cancel and explicitly repair dependencies as appropriate. A parent cannot be marked done while unfinished children remain.
- CLI/API share strict validation and deterministic formatting. Mutations use a worktree-local lock, atomic per-file writes, and expected revision checks. Direct edits remain supported, but editors do not participate in that lock; run `pnpm tasks:check` before publishing. Malformed files must never be treated as an empty store or overwritten silently.
- A crash can leave `.relay/.tasks.lock-gate/`; this gate deliberately fails closed. Stop Relay and other task commands before manually removing an abandoned gate, then rerun validation. Never remove a live writer’s lock.
- `relay tasks archive --days 30` moves old done/cancelled tasks into tracked history; run it in scheduled maintenance, never as a read side effect. Reopening restores a task to the active directory. Canonical history stays in Git; generated indexes/locks are disposable.
- `relay tasks migrate --dry-run` then `--apply` converts a legacy `.relay/tasks.json`, preserves IDs/fields/references, and archives existing terminal records. Legacy snapshots are read-only until migrated; never dual-write the two formats. Rebase old branches across migration and translate remaining snapshot edits.
- Unrelated task files merge normally. Resolve competing edits to the same task explicitly, regenerate updatedAt, and validate the merged graph. Never use a union merge driver, last-writer-wins timestamps, or “done always wins.” Agents may independently pick up work in separate Spaces; no global claim service exists.
- Core: `server/core/task-manager.ts` and helpers, no server dependencies. Task CRUD stays under `/api/projects/:id/tasks`; detail and comments load on demand. Space-scoped updates invalidate matching UI queries. Provider task_list activities remain separate from these repository tasks.
- Provider-watch may publish accepted task intake and bookkeeping without a PR, in an isolated maintenance worktree. Source implementation still requires a code PR. See `.relay/provider-watch-prompt.md`; never push unrelated files or force-push.

## Common Pitfalls

- **`#` imports**: All imports in `server/` and `cli/` use `#core/` or `#server/` aliases. No relative path navigation (`../`).
- **`.js` extensions**: All `#` imports must use `.js` extensions (ESM + NodeNext resolution).
- **Build before test**: Tests import from `dist/`, not source. A stale build = confusing test failures.
- **`import.meta.dirname`**: `server/http.ts` detects whether it's running from source or `dist/` to compute the project root. Avoid hardcoded `../..` traversals — use the `projectRoot` constant instead.
- **No parameter properties**: Node's native TS type stripping doesn't support `constructor(private x: T)` syntax. Use explicit field declarations + assignment instead. (This is what enables `pnpm dev` to run without tsc.)
