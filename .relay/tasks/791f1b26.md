**What changed**: SDK 0.3.198 added a `request_timeout_ms` option to the `mcp_set_servers` control request, allowing per-MCP-server timeout configuration.

**Bucket**: 2 (capability-declaration)

**ProviderCapabilities / abstraction**: Relay reads MCP server config from `~/.claude.json` and project settings, then calls `mcp_set_servers` when a Claude session starts. The new option is a per-server `request_timeout_ms` field in the servers array. Consider adding a `requestTimeoutMs?: number` to Relay's stored MCP server config shape and threading it through the driver call.

**UI control**: Surface a timeout field per MCP server entry in the project settings MCP section. If per-server MCP options aren't yet in the settings UI, this is a small prerequisite. At minimum, pass a configurable default (e.g. 30 000 ms) in the driver to prevent infinitely-hanging tool calls.

**Scope estimate**: Medium. (1) Add `requestTimeoutMs?: number` to the MCP server config shape in types. (2) Thread it through to `mcp_set_servers` in the Claude SDK driver. (3) Persist via project settings API. (4) Render in project settings UI.

**Changelog ref**: @anthropic-ai/claude-agent-sdk 0.3.198

---

**Kickback note (2026-07-22):** Two blockers: (1) SDK is pinned at 0.3.197; `request_timeout_ms` was added in 0.3.198, so the option isn't in the installed SDK. (2) More fundamentally, `claude-sdk.ts` never calls `setMcpServers` at all — MCP servers for Claude sessions are configured via the Claude CLI (`claude mcp add`) and read automatically by the SDK from `~/.claude.json`/`.mcp.json` at startup. Implementing this task requires a design decision about whether Relay should call `setMcpServers` explicitly at session start (bypassing CLI-based config), and if so, how to reconcile with the CLI-managed server list. That design decision must come first. Needs human design before re-queuing.
